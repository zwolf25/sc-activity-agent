# Architecture

How the SC Activity Agent works and why it is built this way. Update this file with every change that alters a decision below.

## What it is for
It creates believable ServiceChannel activity for demos, testing and training. Believable means two things. Every action goes through the API as the right kind of user (Subscriber or Provider), so the audit trail looks like real work. And each work order follows a full lifecycle at human pace, with notes that fit the situation.

## Shape of the system
One Python process runs two things: an engine loop and a localhost web console. Everything it knows is in one SQLite file per instance. The desktop app wraps that same process; see "Desktop app" below.

```
 console (FastAPI + Jinja)  --reads/writes-->  SQLite (agent.db)  <--reads/writes--  engine loop
                                                                                       |-- Creator: makes new WOs
                                                                                       |-- Engine: runs due plan steps
                                                                                       '-- ScApp: OAuth, rate limit, audit log
```

| Module | Job |
|---|---|
| `store.py` | SQLite schema, encrypted secrets, settings, versioned migrations; one SQLite connection per thread (engine, web and sweep threads run at once, and one shared connection raises InterfaceError on overlap) |
| `client.py` | OAuth password grant per user, token cache, rate limiter, audit log, pause guard |
| `planner.py` | Builds the whole plan for one WO, with times, before the WO exists |
| `engine.py` | Runs due steps in order, retries with backoff, handles pauses and sleep gaps |
| `handlers.py` | One executor per step kind; picks the mapped user and calls the API |
| `creator.py` | Rolls daily WO counts, picks issues, creates WOs, saves their plans |
| `generator.py` | Pure helpers: issue flattening, Rank 1 trades, picking, payloads |
| `content.py` | Note templates keyed by role and situation |
| `alerts.py` | Optional Telegram alerts and action buttons: outbound only (sendMessage, getUpdates long poll), never raises into the engine |
| `status.py` | Dashboard counts, the This week table, step context text |
| `web/` | The console (routes in `app.py`, Jinja templates, one stylesheet) |
| `autostart.py`, `launcher.py`, `cli.py` | Start at login, launcher, commands (source installs; the desktop app does its own login start) |
| `update.py` | Daily release check, the pending-update banner, `agent update` for source installs, and database backups (last 10 kept; also taken before every clean-up run) with `agent backup [name]` to list or restore |
| `welcome.py` | First-run environment choice in the desktop app |
| `src-tauri/` | Desktop shell (Tauri v2, Rust): window, tray, sidecar control, updater, login start |
| `packaging/` | `sidecar.py` entry point and `build_sidecar.sh` (PyInstaller) |
| `desktop/` | The loading page the window shows until the agent is ready |
| `.github/workflows/` | `ci.yml` tests, `release.yml` builds and attaches the release files, `desktop-check.yml` builds the installers unsigned on every change to desktop code |

### Desktop app (since 0.3.0)
The desktop app is a second way to run the same agent, for people without Python. Two programs ship together. `src-tauri/` is a small Tauri shell (Rust). `packaging/build_sidecar.sh` freezes the Python agent with PyInstaller into one executable, `agent-core`, which Tauri bundles next to its own binary.

The shell starts `agent-core --data-dir <app data folder> run` with `SC_AGENT_PACKAGED=1`, waits for the agent to write its port to `<data folder>/port`, then points its window at `http://127.0.0.1:<port>/`. Closing the window hides it; the tray keeps the agent running. Quit asks the agent to stop with `POST /shutdown` (the frozen program is two processes, a PyInstaller loader and Python, so killing the loader would leave the port taken), then kills it if it does not stop in 5 s. A supervisor thread in the shell polls the agent program every 2 s: a clean exit is only logged, an abnormal exit (non-zero status or a signal) is logged to `agent.log` as `[shell <epoch>] agent program exited with ...` and the program is started again after 5 s doubling to 5 min (reset after 2 min of uptime). The shell starts it with `PYTHONUNBUFFERED=1` and `PYTHONFAULTHANDLER=1`, and `cmd_run` line-buffers stdout, because a buffered log is lost when the system kills the process (2026-10-28: macOS killed the child about 2 s after the console opened when the app was launched from Finder or `open`, but not from a terminal or launchd; cause not found).

The app's data folder is the OS app-data folder for the bundle id `com.zackwolf.sc-activity-agent` (macOS `~/Library/Application Support/`, Windows `%APPDATA%`). It holds `agent.db`, `secret.key`, `port`, `agent.log`, `first-run-done` and the update backups. Each copy of the app is one instance with one locked environment, like a source install; for the other environment a person uses a source install or a second data folder.

`PACKAGED` mode changes four things: the agent picks the first free port from 8080 and records it; a first-run welcome page (`welcome.py`) asks Production or SB2 and locks the choice, as `agent init` does; `/shutdown` and `/update/prepare` exist; the Settings login switch is hidden, because the tray menu owns Start at login (the Tauri autostart plugin; the first launch turns it on, as the Hub does). The SB2 copy (B-45) is a second instance in `<data folder>/sb2` with its own DB, key and port (first free from 8081), started on demand by Connections > Open SB2 test instance (`launcher.run_cmd` runs the frozen program with `--data-dir`, as the shell does). Each instance keeps its locked environment; this is not a switch. `/update/prepare` and `/shutdown` pass the call to the other instance if its port answers (`?cascade=0` stops the bounce), so an update or Quit from either console covers both. The Production agent restarts the SB2 copy at startup when that copy was running at update time (`resume_after_update` still set). The tray also has Production console, SB2 console (opens Connections when SB2 is not running), Open console, Keep Mac awake and Quit. Keep Mac awake (macOS only, on by default, saved in `<data folder>/keep-awake`) runs `caffeinate -i -s -w <app pid>`: plans only run while the machine is awake and every sleep shifts the remaining steps later, so the shell blocks idle sleep on power; `-w` ends it with the app. Lid-close and battery sleep are not covered. Windows has no equivalent yet. One launch at a time is enforced with the single-instance plugin: opening the app again shows the existing window.

On an update the shell stops the old agent through `/shutdown`, and on every start it replaces a stale agent still holding the port. The welcome page only moves on by itself when its own button was clicked in the window; if the environment was set another way, relaunch the app.

Updates use the Tauri updater with the Hub's design: `latest.json` on the latest GitHub Release, signed with a minisign key whose public half is in `tauri.conf.json` and whose private half is a repo secret. The console's Update now button calls `/update/prepare` (pause, copy the database, set `resume_after_update`), runs the updater, calls `/shutdown`, then relaunches. The new version resumes the agent on start only if the update paused it. A page served from `127.0.0.1` can call the updater because `capabilities/default.json` lists that origin as remote. The banner comes from the agent's own hourly check of GitHub Releases (`update.pending` hides a cached release once the running version has caught up), so a new release can take up to an hour to show; the updater itself looks at `latest.json`.

**Release pipeline.** Publishing a GitHub Release runs `release.yml`: the Python wheel and sdist on Linux, and on macOS and Windows the sidecar build, then `tauri-action`, which attaches the `.dmg`, the Windows `.exe` and `.msi`, their `.sig` files, the updater tarball and `latest.json`. The version lives in four files (`__init__.py`, `tauri.conf.json`, `package.json`, `Cargo.toml`) and a test fails if they differ. Secrets: `TAURI_SIGNING_PRIVATE_KEY` (empty password, so no password secret). A tag and Release cannot be redone, so run `desktop-check.yml` before tagging.

TLS: the frozen Python has no system CA bundle, so `client.SSL_CONTEXT` verifies against `certifi` for both the ServiceChannel calls and the update check. This was found when the 0.3.0 app never showed the update banner.

Why a shell and not PyInstaller alone: replacing a running executable on Windows is the hard part of an updater, and Tauri already solves it. The macOS sidecar needs the `disable-library-validation` entitlement (`entitlements.plist`): Tauri re-signs it ad hoc, and macOS then refuses to load the Python framework PyInstaller unpacks.

Not done on purpose: Apple notarization and Windows code signing (cost; same choice as the Hub), an Intel Mac build (`macos-latest` runners are Apple silicon), Linux. The update cycle ran for real on macOS arm64 (0.3.2 to 0.3.3 through the Update now button: pause, backup, install, relaunch, resume). The Windows installer and updater have only been built on CI, not run on a Windows machine. A browser-downloaded Mac app also meets Gatekeeper (right-click Open), which was not part of the local test.

## Decisions and the reasons

**Two instances, no environment switch.** Production and SB2 each get their own data folder, database, key and port. The environment is chosen at `init` and locked. A switch would risk pointing a running Production plan at the sandbox, or the reverse. Integration apps are registered per environment anyway, so nothing could be shared.

**A saved plan per work order.** `planner.build_plan` rolls every outcome once (visits, late arrival, proposal, rejections) and stores the timed steps. The engine only executes them. This makes the agent restart-safe, makes behavior inspectable, and lets sleep-gap handling re-time steps without re-rolling.

**Subscriber and Provider act separately.** `Runtime.user_for` in `handlers.py` picks randomly among the users whose `can_do` list holds the action. Provider-side steps are limited to users of the WO's provider (`provider_id` in the WO ctx, set at creation from the Rank 1 owner of the trade and at clean-up takeover from the WO's Provider; WOs without one fall back to every capable user). A check-out reuses the tech who checked in for that visit, kept in ctx `techs` (`"visit.tech" -> user id`), because a real tech leaves the same visit they entered. With probability `multi_tech` a visit gets a second tech (`tech=1` check-in 5 to 20 minutes after the first, check-out a little after the first tech's); with no second check-in tech the extra steps end as done without a call (`Skip`). The first tech out of a crew visit carries `partial` and checks out as Parts on Order, because Completed closes the WO and the second tech's check-out then fails with 921 (verified on Prod 2026-10-27); the check-out handler ignores `partial` when no second tech checked in. Why capabilities on the user: real accounts have several technicians across provider accounts, and one user per role looked fake.

**Only trades where we are Rank 1.** SC assigns a new WO to the Rank 1 provider for that trade and location. If another provider holds Rank 1, SC accepts the WO without error and assigns it to them, and the agent could not move it forward. So `creator.our_trades` checks Rank 1 through the rank endpoints (cached for a day) and never creates other trades. `creator.resync` forces that read (the Locations page Refresh now button) and also records the issue-list trades we skip, so a Rank 1 change shows up without waiting a day and the skipped trades are visible instead of silent. Adding many locations goes through one `add-many` route that takes ticked rows and pasted IDs and never resets an existing location's enabled flag.

**Never retry a failed create.** A rejected create leaves a VOID shell WO that the API cannot remove. The creator drops the slot on failure and records the error. Steps for existing WOs do retry, with backoff.

**Check that an issue resolves before creating it.** `POST /workorders` looks the issue up on the location's own dashboard, not on the `IssueListHeaderId` we send. Dashboard 3151 holds many issues that the location's dashboard lacks, and creating one fails with "Cannot find issue choice" and leaves a permanent VOID shell. `GET /issuelist/issuechoice` without `setupId` does the same lookup read-only, so `creator._resolves` calls it first (400 means skip, cached) and redraws up to 8 times. The `setupId` form is not a valid check, because it validates against the named dashboard and passed for every failing issue.

**Check-in needs a pair-level permission.** ServiceChannel enables XML or GPS check-in/out per Subscriber and Provider pair, not per user. Without it the API returns 403 (804). The handler turns that into an error that names the permission. A pre-flight check is not possible without a write, so the first check-in is the test. The Setup page reads the audit log: a pair is Confirmed after a successful `universalCheckIn` by one of its users, Blocked when the latest one returned 403, and otherwise not confirmed yet. It is a card, not a setup step, because the first check-in can be days away and the setup gate would trap new users on the Setup page.

**Cancel is COMPLETED/CANCELED.** The API cannot set VOID. `handlers.cancel_wo` sets that status as the Subscriber and skips the plan's remaining steps. The Cleanup page uses it for the agent's own WOs. `cleanup.py` handles the other WOs at the same locations (B-41): `preview` reads OData `UpdatedDate lt cutoff` per enabled location and drops the agent's own WOs and anything with the protect label, saves the list, and `run` re-reads each WO with `GET /workorders/{id}` before a Subscriber status PUT, so a WO touched after the preview is skipped. It runs in a thread, writes progress to the `cleanup_run` setting, and never changes the `work_orders` table. `sweep` (B-40) runs the same preview and run once per weekday from the main loop, in a thread because two calls per WO at 15 calls/min would stall the step engine; it caps at 100 WOs a day. Saving the daily choice sets `last_sweep` so a run never follows within minutes, and `finish` acts as off on Prod: it speaks as the Provider on real work orders (a v0.5.0 sweep did this on Prod by accident on 2026-10-27 and was paused and skipped). `finish_plan` gives a WO held by one of our providers a visit, review, invoice, approve plan (no accept: idle WOs are mostly past it and the API returns 904) fitted to the activity window. Why preview-then-confirm (manual path): it cancels data other people may own on a shared Subscriber, so nothing runs without a reviewed list. The API rejects VOID with error 904 for any value.

**Audit log and Errors answer different questions.** Audit is every API call (what happened). Errors is the queue of failed steps and creates with Retry and Skip (what needs a person). The Audit log has a failures-only filter, and Errors links into it by WO.

**NTE and category come from the issue list.** The dashboard issue list is the source of truth for trade, category, priority and NTE, so they are not settings. The dashboard is a setting on the Subscriber connection because dashboards belong to users in ServiceChannel, not to locations. The agent reads the chosen dashboard explicitly. `storedashboards/current` follows whichever dashboard the token user last used, which is not stable.

**No LLM at runtime.** Notes come from templates filled with WO details and seeded phrase variation. This costs nothing per run and gives the same behavior every time.

**Pause is the only control.** There is no kill switch or dry run. Pause blocks every write at the client, so no code path can skip it. Resuming applies a gap policy to the overdue steps.

**Sleep gaps.** The engine records a heartbeat each tick. A gap over ten minutes is recorded and the remaining steps of affected WOs shift forward by the gap, snapped to activity hours, so spacing and order survive and check-out stays after check-in on the same day. The Dashboard shows the gap so it can be re-resolved.

**Backups are copies of `agent.db`, restored only while the agent is stopped.** A running agent holds open connections, and swapping the file under them would corrupt the next write. So the console can back up and list, and restoring is the CLI (`agent backup <name>`), which refuses while the pid in `agent.pid` is alive and saves the database it replaces first. Machine move = copy the data folder; there is no separate settings export, because the database holds the settings, the encrypted secrets and the key sits beside it.

**Updates are opt-in.** The agent checks GitHub Releases hourly and shows a banner; nothing installs by itself. Source installs run `agent update` (also Settings > Check for updates and the banner button): pause, back up the database, `pip install` the tag archive (a zip from GitHub, so the machine needs no git), let the new code migrate the schema, resume, and if the new version fails to start restore the database and reinstall the previous tag. Afterwards `update._restart` starts the agent again, except under the desktop app or a Start at login unit, which restart it themselves (a second copy would run every step twice).

**Python install path (B-49 outcome).** The packaged desktop program is killed by macOS about 2 to 15 s after it opens when launched outside a terminal (ad-hoc signed, not notarized; probably security software). A source install is not: on 2026-10-28 the venv `agent run` survived under launchd and from a Finder-style `open` of the launcher app with live API calls. So `install.sh` and `install.ps1` are the supported install for machines that cannot run the desktop app. They check `requires-python`, print install steps when Python is missing, build a private venv under `~/.sc-activity-agent-app` (the data folder stays separate and is never touched by an update) and run `agent install-app`. `awake.py` runs `caffeinate -i -s -w <agent pid>` from the run loop while the Keep awake setting (default on, macOS only) is on, for the reason the desktop shell does it: plans only run while the machine is awake. `-w` ends it with the agent, and the loop stops or starts it when the setting changes. The launcher (`launcher.py`) runs `agent open`, which starts `agent run` when the port is closed and shows an alert naming agent.log when it cannot. `pyproject.toml` lists the web templates and styles as package data: without it a pip install had no console pages. The desktop app does the same steps with the Tauri updater (see above) and treats its own sidecar and shell as one unit, so they always update together.

**Localhost only, secrets encrypted.** The console binds to 127.0.0.1 with no login. Secrets are Fernet-encrypted in SQLite with a key file in the data folder.

### Telegram alerts
Why outbound only: the agent runs on a user's laptop with no public address, so alerts are `sendMessage` calls and button taps are read with `getUpdates` long polling in a daemon thread. Why one bot per instance: Telegram lets one program read a bot's updates, so Prod and SB2 each have their own token (`alerts_token`, encrypted) and settings (`alerts`), and messages carry a [PROD]/[SB2] tag. Why limits: 6 h cooldown per alert key and 10 messages an hour with one summary, so a bad night cannot flood a phone. Why a chat check: only the saved `chat_id` may tap; Cancel WO needs a yes; a stale button re-reads the live step state. A failed send is stored in `alert_error` and never stops the engine. Taps are logged in `changes`.

## Data model
`connections` and `users` hold integration apps and their users. `users.can_do` is a JSON list of actions the user may do (set with the Can do checkboxes on Connections). The old `roles` table is kept but unused for one release; migration 1 converted its `*` rows to `can_do` and dropped per-location overrides. It is removed in 0.6.1. `locations` describes where the agent works. `work_orders` and `steps` hold each WO and its plan. `api_log` is the audit trail. `settings` holds everything else as JSON.

## Known limits
- The invoice reject-then-resubmit path (B-37) is unit-tested but has not run live: no SB2 WO has rolled the 5% reject branch yet. The invoice number includes a per-WO counter so the resubmission is not a duplicate.
- `docs/api-notes.md` lists what is verified on SB2 and in Production. Production check-in and invoices were still untested at the time of writing.
- Locations come from a list the app loads from the Subscriber (`GET /odata/locations`, paged 50 at a time, cached in the `locations_cache` setting). The user adds or removes from it, so nobody types ids; a typed Prod id that differs from SB2 would break the contract check and every create. Verified on SB2: 50 locations, response wrapped in `value`, paging stops on an empty page.
- **SB2 copy only from Production.** An SB2-first install cannot add Production, because the SB2 copy hangs off the Production instance. Two programs run while SB2 is on, each with its own rate limit.
- **No import tool; moving an instance is a folder copy.** The desktop app starts empty. To adopt an existing instance, stop it, copy its data folder (`agent.db`, `secret.key`) into the app's data folder, and start the app. The environment and port live in the DB, so the welcome page is skipped and the app reuses the port once the old process has released it. Done once for Prod on 2026-10-27 (see CHANGELOG); the old login item must be removed so two agents never act on the same plans.
- **Step failures:** the engine fails any step whose handler raises, not only API errors, so a handler bug cannot loop on one step forever. Each loop in `agent run` (steps, update check, creator) also catches its own errors so one failure never stops the others.
- **Proposals:** the Provider creates the proposal (it has no WO field), and the Subscriber links it with assignWO before approving, because assignWO is Subscriber-only.
- **The user may act first:** `proposal_decide` and `invoice_decide` read the live status before acting. If the user already did what the plan wanted, the step is done and the plan continues. If the user rejected a proposal the plan meant to approve, the plan adds a revised proposal and decision (at most 3 times, then the step fails for the Errors page). A decision the user already made is never overturned, because the API allows an approve after a reject. `invoice_pay` runs as the same Subscriber user as `invoice_decide` (so existing instances need no new role row), pays only an invoice that is still APPROVED, and waits `pay_days` (default 30, spread about 25%) after the approval, because Net 30 is the common term. A WO therefore stays active for a month after its decision and shows as Payment due until then. It quietly skips a Subscriber the API says cannot record payments (error 1178 "Pay not allowed"). Other steps do not yet check live state (B-39: reschedule, NTE and priority edits remain). Every write step first runs `preflight` (one GET of the live WO): a cancelled WO ends the plan before any write, and a WO a user already completed skips accept, check-in, check-out and proposal steps (review and invoice still run). A failed preflight read is ignored and the step runs; a refused write re-reads the WO in `guarded` as before. Why read first instead of reacting to a failure: some writes on a changed WO succeed or leave odd audit entries, and one GET per step (about 12 per WO) is far cheaper than polling every WO. A `watch` pass (behavior `watch`, default off; every 3600 s, 1 WO per pass, least recently watched first) only keeps the dashboard fresher.

**Declines and reschedules (B-11):** `decline` and `reschedule` use the Provider's `accept` capability (no new checkbox). A decline plan is only `decline` then a Subscriber `cancel` 1 to 3 days later (reason 1, 2, 3 or 6; reason 5 needs custom text; the decline has no `Note` because that returns 501). A reschedule plan puts the original date in the WO at creation (`reschedule.from_ts`, read by `Creator.create`), then moves it later with `PUT /workorders/{id}/scheduledate`; the visits are planned on the new date, and a provider note explains the change. Reschedules are skipped for emergency, proposal and late plans. Whether a decline shows OPEN / DECLINED depends on the trade's auto-reassign setting (api-notes). B-20 builds on this.

**Emergency plans (B-08):** `planner.build_plan(..., eta=...)` treats an ETA at most `emergency_hours` after the call date (default 8, 0 = off) as an emergency; the priority label never decides. `Creator.create` picks a same-day ETA for EMERGENCY issues (we choose the ETA of the WOs we create, so the label is only the trigger for that choice), and `cleanup.finish_plan` reads the WO's real `CallDate` (or `CreatedDate`) and `ScheduledDate`, and only counts a visit still ahead. The accept moves to 2 to 15 minutes, a subscriber follow-up and a provider ETA note form the confirm-availability exchange, the first check-in lands under about 8 hours out (fitted to activity hours), and proposals and late arrivals are switched off, since an urgent visit that waits days for a proposal looks fake.
- **One command surface for changes:** settings and plan edits (`get`, `set`, `plan`, `step`) go through the CLI and the same SQLite store the console uses, and each change is logged in the `changes` setting. A person, the console or an assistant acting for the user all use it, so nobody edits the database by hand. The handlers also stop at a WO the user cancelled or completed (`guarded` in `handlers.py`).
- The `contracts` table is unused. Rank 1 trades live in the `rank1` setting (written by the creator, cached a day), and the Locations page reads them from there. Drop the table with a migration when convenient.
- **Every planned step is fitted to the activity window.** The planner draws times by adding random offsets to the creation time, so notes, review and invoices used to land at night and on weekends. `planner._fit` moves any step outside the window to the start of the next business day and keeps the order, spreading consecutive moved steps a few minutes apart. Moving by time-of-day was tried first and failed: evening steps landed late in the afternoon and pushed the next morning's check-in past closing. Plans already saved keep their old times; re-time them by hand (`agent step <id> due ...`) if it matters.
