# Architecture

How the SC Activity Agent works and why it is built this way. Update this file with every change that alters a decision below. The maintainer's `sc-activity-agent-doctor` skill keeps a digest of this file; the release process refreshes it.

## What it is for
It creates believable ServiceChannel activity for demos, testing and training. Believable means two things. Every action goes through the API as the right kind of user (Subscriber or Provider), so the audit trail looks like real work. And each work order follows a full lifecycle at human pace, with notes that fit the situation.

## Shape of the system
One Python process runs two things: an engine loop and a localhost web console. Everything it knows is in one SQLite file per instance.

```
 console (FastAPI + Jinja)  --reads/writes-->  SQLite (agent.db)  <--reads/writes--  engine loop
                                                                                       |-- Creator: makes new WOs
                                                                                       |-- Engine: runs due plan steps
                                                                                       '-- ScApp: OAuth, rate limit, audit log
```

| Module | Job |

## Decisions and the reasons

**Two instances, no environment switch.** Production and SB2 each get their own data folder, database, key and port. The environment is chosen at `init` and locked. A switch would risk pointing a running Production plan at the sandbox, or the reverse. Integration apps are registered per environment anyway, so nothing could be shared.

**A saved plan per work order.** `planner.build_plan` rolls every outcome once (visits, late arrival, proposal, rejections) and stores the timed steps. The engine only executes them. This makes the agent restart-safe, makes behavior inspectable, and lets sleep-gap handling re-time steps without re-rolling.

**Subscriber and Provider act separately.** `Runtime.user_for` in `handlers/runtime.py` picks randomly among the users whose `can_do` list holds the action, once per step: the pick is saved in the step payload (`user`) and every call in that step and every retry reuses it. **Fallback user:** when a step uses up its 3 attempts on a user-bound refusal (403, an opaque 501, 921; `engine.user_bound`; "Invalid WorkOrder status" and 5xx never count), `Engine` calls `Runtime.rotate_user`, which moves the pinned user into payload `tried` and the step gets a fresh 3 attempts with another capable user. The step fails and alerts only when every capable user has failed. Check-in and check-out never rotate (the visit keeps its tech). An operator `step retry` clears `user` and `tried`. Why: a real org sends an invoice over one approver's limit to another approver. Why: before v0.12.3 each API call picked again, so one review mixed two users and a retry could switch users; on 2026-11-02 Prod that gave 403 "exceeds user Limit", 501 and 921 on one user while another user's call went through. **Approval limits:** for `invoice_decide` and `proposal_decide`, `Runtime.candidates` keeps only Subscriber users whose `UserProfile.Limits.InvoiceLimit` or `ProposalLimit` `.Amount` covers the total being decided (ctx `amount`, saved by `invoice_submit` or `proposal_create`; the invoice's value replaces the proposal's). Limits come from `GET /users/current/profile` and are cached in settings key `user_limits` for an hour; an unreadable profile counts as no limit so a profile outage cannot stall invoices. When nobody qualifies the step fails with a message to raise a limit. Why: Prod user jhef123 has a limit of 0 and drew 33 403s "Invoice Amount exceeds user Limit" (0 approvals), each costing 3 attempts and about 13 minutes before the rotation moved the step to ProductTeam (limit 100000). `engine.over_limit` is the backstop for a stale cached limit: that 403 rotates at once instead of after 3 attempts. Provider-side steps are limited to users of the WO's provider (`provider_id` in the WO ctx, set at creation from the Rank 1 owner of the trade and at clean-up takeover from the WO's Provider; WOs without one fall back to every capable user). A check-out reuses the tech who checked in for that visit, kept in ctx `techs` (`"visit.tech" -> user id`), because a real tech leaves the same visit they entered. With probability `multi_tech` a visit gets a second tech (`tech=1` check-in 5 to 20 minutes after the first, check-out a little after the first tech's); with no second check-in tech the extra steps end as done without a call (`Skip`, defined in `client.py`, raised by `Runtime.user_for` and ended once in `Engine.tick`; B-104, because catching it in `checkio` and `guarded` missed the live-WO read in `preflight` and failed step 1350 with a blank error). The first tech out of a crew visit carries `partial` and checks out as Parts on Order, because Completed closes the WO and the second tech's check-out then fails with 921 (verified on Prod 2026-10-27); the check-out handler ignores `partial` when no second tech checked in. Why capabilities on the user: real accounts have several technicians across provider accounts, and one user per role looked fake.

**Only trades where we are Rank 1.** SC assigns a new WO to the Rank 1 provider for that trade and location. If another provider holds Rank 1, SC accepts the WO without error and assigns it to them, and the agent could not move it forward. So `creator.our_trades` checks Rank 1 through the rank endpoints (cached for a day) and never creates other trades. `creator.resync` forces that read (the Locations page Refresh now button) and also records the issue-list trades we skip, so a Rank 1 change shows up without waiting a day and the skipped trades are visible instead of silent. **Rank 1 read can be wrong (v0.20.4):** on Prod 2026-11-06 `GetPrimaryRankedProviderLocations` named GriffCo Rank 1 for HVAC at ZW123 while two contracts existed (AHS Services Co and GriffCo) and SC routed new WOs to AHS, a provider with no connection here, so accepts failed with 502. So `creator._create` reads the new WO (`GET /workorders/{id}`, `Provider.Id`) right after the POST. A provider that is one of ours wins over the cache for `ctx.provider_id`; a provider that is not ours cancels the WO, adds the trade to store key `rank1_foreign` (per store, removed from `our_trades`, cleared by `resync`) and raises a creation error. Why not just trust the cache: the rank endpoints do not show ties or another provider's contract. Adding many locations goes through one `add-many` route that takes ticked rows and pasted IDs and never resets an existing location's enabled flag.

**Never retry a failed create.** A rejected create leaves a VOID shell WO that the API cannot remove. The creator drops the slot on failure and records the error. Steps for existing WOs do retry, with backoff.

**Check that an issue resolves before creating it.** `POST /workorders` looks the issue up on the location's own dashboard, not on the `IssueListHeaderId` we send. Dashboard 3151 holds many issues that the location's dashboard lacks, and creating one fails with "Cannot find issue choice" and leaves a permanent VOID shell. `GET /issuelist/issuechoice` without `setupId` does the same lookup read-only, so `creator._resolves` calls it first (400 means skip, cached) and redraws up to 8 times. The `setupId` form is not a valid check, because it validates against the named dashboard and passed for every failing issue.

**Check-in needs a pair-level permission.** ServiceChannel enables XML or GPS check-in/out per Subscriber and Provider pair, not per user. Without it the API returns 403 (804). The handler turns that into an error that names the permission. A pre-flight check is not possible without a write, so the first check-in is the test. The Setup page reads the audit log: a pair is Confirmed after a successful `universalCheckIn` by one of its users, Blocked when the latest one returned 403, and otherwise not confirmed yet. It is a card, not a setup step, because the first check-in can be days away and the setup gate would trap new users on the Setup page.

**Cancel is COMPLETED/CANCELED.** The API cannot set VOID. `handlers.common.cancel_wo` sets that status as the Subscriber and skips the plan's remaining steps. The Cleanup page uses it for the agent's own WOs. `cleanup.py` handles the other WOs at the same locations (B-41): `preview` reads OData `UpdatedDate lt cutoff` per enabled location and drops the agent's own WOs and anything with the protect label, saves the list, and `run` re-reads each WO with `GET /workorders/{id}` before a Subscriber status PUT, so a WO touched after the preview is skipped. It runs in a thread, writes progress to the `cleanup_run` setting, and never changes the `work_orders` table. `sweep` (B-40) runs the same preview and run once per weekday from the main loop, in a thread because two calls per WO at 15 calls/min would stall the step engine; it caps at 100 WOs a day. Saving the daily choice sets `last_sweep` so a run never follows within minutes, and `finish` acts as off on Prod: it speaks as the Provider on real work orders (a v0.5.0 sweep did this on Prod by accident on 2026-10-27 and was paused and skipped). `finish_plan` gives a WO held by one of our providers a visit, review, invoice, approve, pay plan (the pay step comes `pay_days` after the decision, as in `planner.build_plan`; without it the WO sits in Payment due with nothing pending; no accept: idle WOs are mostly past it and the API returns 904) fitted to the activity window. Why preview-then-confirm (manual path): it cancels data other people may own on a shared Subscriber, so nothing runs without a reviewed list. The API rejects VOID with error 904 for any value.

**Hand-made WOs get a plan (B-51).** `pickup.py` runs once an hour from the main loop when the Settings toggle "Plan work orders people create by hand" is on (store key `pickup.on`, default on; it writes as the Provider and Subscriber on WOs the agent did not create, so the guards below are the safety). It lists WOs created in the last 7 days (`pickup.days`) at each enabled location (OData `CreatedDate gt` with `Provider` expanded) and keeps only those that pass every guard: not already in `work_orders`, held by one of our provider connections, in a trade where Rank 1 at that location is ours (`Creator.our_trades`), active, and without the protect label (the same label the clean-up honors). Each candidate is re-read with `GET /workorders/{id}` before planning, because the list can be stale. `cleanup.finish_plan(accept=True)` then builds the plan: an accept step first when the WO is still OPEN (a fresh WO is OPEN with an empty extended status, and an accepted one is IN PROGRESS / DISPATCH CONFIRMED), then visit, review, invoice, decision, all fitted to the activity window. WOs held by providers we have no credentials for are ignored, not cancelled: a person may be working them, and the clean-up (B-40/B-41) already handles idle ones. Each pass plans at most 10 WOs, oldest first. Why a toggle: a Prod owner can switch it off; the v0.5.0 sweep acted on real Prod work orders by accident (2026-10-27), which is why every guard must pass and why an update that turns this on says so in the CHANGELOG. Shortcut: the pass runs in the main loop, so about 12 calls at 15 calls/min hold the step loop for about a minute an hour; move it to a thread like the sweep if that shows.

**Checklists are answered at check-out (B-22).** `handlers.checklists.build`'s `answer_checklists` runs first in `check_out` for the primary tech when the Settings toggle "Answer checklists at check-out" is on (store key `checklists.on`, default off: it is a new kind of write, and Production has not been checked). It reads the checklists the location has for the WO's trade (`GET /checklists/detail`, which needs the location's Subscriber id), then posts one answer per question as multipart (`ScApp.call(parts=...)`): `on` for acknowledgements, a random non-follow-up option for selectors, a provider note for text, a small count for numbers, and the WO's photo set (side by side) where a picture is asked for. The attempt number is the visit, so a second visit answers again; the visit is saved in `ctx.checklists` so a retried check-out does not repeat it. It is fail-soft: an API refusal is audited and skipped so the check-out still goes through, and only a pause stops it. The photo set id is saved in `ctx.photo_set` so every later photo on that WO (B-52, B-53) comes from the same scene. We chose the library as files in the repo, not a download, so a clean install works offline and the photos are reviewed by us once. Questions per asset are still skipped. Answers carry the answering user's own id (`AuthUserID`, read once from `/users/current/profile` into `users.sc_user_id`; `TechnicianID` 1 only when the profile gives no id). A required question the agent cannot answer (per-asset, an unknown type, a selector with no usable option) is written to the audit log as `checklist_required_open`, because ServiceChannel will not submit a checklist with a required question open.

**Daily limits (B-71).** `caps.check` runs first in each loop pass. It counts today's `create_wo` rows with HTTP below 400 and all `api_log` rows since local midnight, and when either reaches its limit (store key `caps`, defaults 40 WOs and 3000 calls, 0 = off) it sets `paused_at`, the same pause as the Pause button, records `cap_hit`, and sends the `cap_hit` alert. Counting the audit log means the limits survive a restart and need no counters to reset. The defaults sit about 3.5x above the expected load of two locations at 120 WOs a month and above the busiest observed day (764 calls), so only a wrong slider or a plan bug stops here. Resume does not clear the limit: if usage is still over, the next pass pauses again, so raise the limit or wait for midnight. The banner clears once the agent runs under the limit.

**Scheduled SB2 smoke run (B-78).** Unit tests use a fake transport, so API drift (a renamed field, a new required value) only shows when a real call is made. `smoke.run` creates one WO at the first enabled location, sets every pending step due now, ticks the engine until the plan ends, and reports each step; photos, checklists and rework are forced on for the run and restored after. `smoke.tick` is a loop piece that does this every `smoke.days` days (default 7) when the Settings toggle is on, and writes `smoke_last` and an alert (event `smoke`). The run sets `engine.only_wo` so only its own WO's steps are due: the first live run failed because 206 older overdue steps on the busy SB2 instance took every slot. It runs inside the loop with the loop's own engine, not a second one: two engines on one database would run the same step twice. The cost is that the agent does nothing else for the few minutes the 15 calls/min limit makes the run take; that is fine on a test instance and is why it refuses any other environment (`env` must be `sb2`, checked in `run` and in the route). A Production run would also create a real WO. The alert only arrives if Telegram is set up on that SB2 instance (each instance has its own bot settings).

**Recorded responses (B-90).** `scripts/record_fixtures.py` reads one real response per endpoint the agent reads (read-only GETs on a Prod or SB2 instance) and writes it to `tests/fixtures/` with emails, phone numbers and person-name fields replaced. `tests/test_recorded.py` runs the real parsers (`generator.issues`, `rank_one_trades`, `user_dashboard`, `Creator._assigned_provider`) and checks the fields the handlers read (work order, invoice, OData rows, contracts, assets, checklists). Why: hand-written fakes only encode what we believed; the 0.17.x CategoryId bug and the 2026-11-06 provider-routing bug both came from shapes the fakes did not have. When SC changes a shape or a handler starts reading a new field, re-record and add the field to the test. Gaps: the checklist fixture is an empty list (the Prod test trade has no checklist), and write responses (POST bodies and their answers) are not recorded.

**Time zones (B-74).** A location's zone comes from its Subscriber record (`locations.tz`). Plans (`planner.build_plan`), the Creator's daily slots and clean-up already used it. `Engine.snap` and `apply_gap`, which re-time steps after a sleep gap, and the rework return in `handlers/review.py` used the instance `tz` setting, so on an instance set to Denver an Eastern store's steps were pushed into a window two hours off. They now take the WO's location and fall back to the instance zone when the location has none. The instance zone still drives instance-wide things: the daily-limit day (`caps`), the Audit log time stamps and the clean-up sweep day.

**Errors page (B-79).** `error_groups` in `web/app.py` groups failed steps by kind and error text with runs of four or more digits blurred (WO ids differ, the rest does not), so 100 over-NTE invoices become one row with a count, first and last due time and the WO ids. `ERROR_HINTS` adds a one-line cause for known errors (1104, 403 error 100, 429). Retry all and Skip all post the group's step ids to `/steps/group/{action}` and only touch steps still `failed`. **Close out WO (B-103)** posts the group's WO ids to `/wos/close`: it marks each WO `cancelled` and skips its pending and failed steps, after a confirm dialog, and writes nothing to ServiceChannel (a WO at COMPLETED cannot be cancelled by API, 921). Use it for a WO a person finished or cancelled in ServiceChannel. A step error is never blank: `client.describe` stores the exception class when there is no message, in the engine's three error writes and in the alert.

**Secrets in output (B-72).** `cli.masked` replaces strings that start with `gAAAA` (Fernet tokens) and values under keys named token, secret or password with `***` in `agent get`.

**Photo rotation (B-75).** `photos.pick(..., avoid=)` drops the sets in `avoid` from the candidates while another fits; if all are recent it picks among them anyway. Callers pass `photos.recent(store, location)`. A WO keeps one set for its before, after and checklist photos through `ctx.photo_set`.

**Photos on WOs and closing notes (B-52, B-53).** The set is chosen by `photos.pick(trade, kind, rng, issue=...)`, which prefers sets that match the issue text (B-14). Two Behavior sliders, `photo_before` and `photo_after` (percent, both default 0, so nothing is attached until raised; Production has not been checked). v0.11.0 shipped these as Settings checkboxes; the sliders replace them so the share of WOs with photos is tunable like every other rate. Each roll is made at the moment of the write. `before`: `Creator._attach_before` posts a `before` image from the library to the new WO (`POST /workorders/{id}/attachments`) and saves the set in `ctx.photo_set`. `after`: after the final check-out of the primary tech, `attach_after` (`handlers/field.py`) posts a work-complete provider note and attaches the matching `after` image to it (`POST /workorders/{id}/notes/{noteId}/attachments`), from the same set as the before photo. Both run after the real write has succeeded, so every API refusal, even a pause, is skipped: a retry would only fail the check-out or lose the new WO's plan. The two endpoints take different request shapes (an object versus a bare list); `photos.attach_parts` hides that. B-95: `generator.issues` carries `attach_required` from the issue list's `RequireAttachment: "required"`; `generator.payload` then sends `IgnoreAttachmentsRequiredFlag: true` (else the create fails with 916) and `Creator._create` attaches the before photo whatever `photo_before` says. A trade with no photo set gets none. The closing note is an extra note, not the check-out's Resolution text, because the check-out response gives no note id to attach to.

**Due steps take one slot per WO.** `Engine.due` returns only the first unfinished (pending or failed) step of each WO, oldest first, up to `per_tick`. Why: `_tick` skips any step with an unfinished predecessor, and a predecessor can be due later than its successors (a gap shift or reschedule re-times it), so a query that only excluded failed or future predecessors filled every slot with blocked steps and starved the one that could run (SB2, 2026-11-08: 311 overdue, nothing run for three days).

**Star ratings and rework (B-25).** The rated-or-plain roll and the rework roll are saved in the review step payload (`rated`, `bad`), so a retry repeats the same choice. A rating is only posted while the WO is COMPLETED / PENDING CONFIRMATION; in another COMPLETED state the review confirms plainly (feedback gets 501 "Invalid WorkOrder status"), and NO CHARGE or CANCELED is left alone. Two Behavior sliders, `star_rating` and `rework` (percent, both 0 by default). `star_rating` is the share of reviews that carry a rating; `rework` is the share of those rated reviews that are unsatisfactory (so `rework` alone does nothing). The `review` handler rolls `star_rating` first. An unrated review does what it always did: PUT status COMPLETED/CONFIRMED. A rated review posts `POST /feedbacks/workorders/{id}` (Answer satisfactory, 3 to 5 stars), which confirms the WO and replaces the status call. An unsatisfactory review posts 1 or 2 stars with a comment; ServiceChannel moves the WO to IN PROGRESS / UNSATISFACTORY, and `rework` (`handlers/review.py`) inserts a provider note, a return check-in (next visit number), a final check-out and a second `review` (payload `round: 2`), then moves every later pending step back by the length of the rework so the invoice still follows the last review. `rework` (`handlers/review.py`) marks the failed review step `unsatisfactory` in its payload so `status.stage` shows the Unsatisfactory stage (a Dashboard tile) until the return check-in. Only one rework round per WO, so a plan always finishes. The rework is planned at review time, not up front, because it depends on a roll the plan does not know yet. The feedback call is only accepted while the WO is COMPLETED / PENDING CONFIRMATION, so the handler reads the live status first: already CONFIRMED means a person got there first and the step is done; any other status parks the step (Park) for the Errors page. `Engine.due` skips steps behind a failed or not-yet-due earlier step of the same WO (B-66), so stuck plans cannot fill the `per_tick` window and starve other WOs; steps that are all due still run in order within one tick. `Engine.tick` re-reads each step's row just before running it, because an earlier handler in the same tick can insert steps (rework, invoice resubmit) and shift this one's `seq`.

**Behavior slider order.** `web/app.py` `SLIDERS` is ordered by where each behavior first shows up in the WO flow: create (volume, photo, emergency), notes, accept (decline, reassign, no-show, reschedule), proposal, visits (late, first-time fix, time on site, two techs, after photo), review (star rating, unsatisfactory work), invoice (flaws, approval), payment, then the global activity hours last. A new slider is inserted at its place in that flow, never appended. Readers scan the page top to bottom as the life of a WO.

**Audit log and Errors answer different questions.** Audit is every API call (what happened). Errors is the queue of failed steps and creates with Retry and Skip (what needs a person). The Audit log has a failures-only filter, and Errors links into it by WO.

**The shared issue list file.** `sc_activity_agent/SCActivityAgentIssueList.xlsx` is the ServiceChannel upload file for the list we test against (single copy, packaged via `package-data`; notes in `issue-list/README.md`). The Settings page serves it at `GET /issue-list.xlsx`, and `release.yml` attaches it to each release. `tests/test_issue_list.py` checks that every attachment-required issue in it has a photo set. Why: users who load the same list get the same trades and photo coverage. The agent never edits or uploads an issue list; any issue list change is made in this file first.

**NTE and category come from the issue list.** The dashboard issue list is the source of truth for trade, category, priority and NTE, so they are not settings. `POST /workorders` resolves the issue on the Subscriber user's own dashboard and ignores `IssueListHeaderId` (api-notes, 2026-11-03), so a dashboard chosen in the agent could only disagree with what a create uses. B-91 therefore reads the user's dashboard from the profile and shows it read-only on Connections. The agent does not require a particular issue list.

**No LLM at runtime.** Notes come from templates filled with WO details and seeded phrase variation. This costs nothing per run and gives the same behavior every time.

**Pause is the only control.** There is no kill switch or dry run. Pause blocks every write at the client, so no code path can skip it. Resuming applies a gap policy to the overdue steps.

**Activity days.** Behavior > Activity days (`behavior.days` and the top-level key `days`, Monday = 0, default Monday to Friday) replaces the old fixed weekdays in the planner (`_biz_day`, `_fit`), `Engine.snap`, and the daily WO count (`generator.daily_count` spreads `wo_per_month` over `4.2 x days` a month). The page always keeps at least one day, or nothing would ever run. The Cleanup sweep still runs on weekdays only. Hours show as 12-hour AM/PM; the stored value stays a 24-hour integer. The Cleanup sweep follows the same list (it used to skip Saturday and Sunday), so a weekend-only setup still sweeps.

**Sleep gaps.** The engine records a heartbeat each tick. A gap over ten minutes is recorded and the remaining steps of affected WOs shift forward by the gap, snapped to activity hours, so spacing and order survive and check-out stays after check-in on the same day. The Dashboard shows the gap so it can be re-resolved.

**Backups are copies of `agent.db`, restored only while the agent is stopped.** A running agent holds open connections, and swapping the file under them would corrupt the next write. So the console can back up and list, and restoring is the CLI (`agent backup <name>`), which refuses while the pid in `agent.pid` is alive and saves the database it replaces first. Machine move = copy the data folder; there is no separate settings export, because the database holds the settings, the encrypted secrets and the key sits beside it.

**Updates are opt-in.** The agent checks GitHub Releases hourly and shows a banner; nothing installs by itself. Source installs run `agent update` (also Settings > Check for updates and the banner button): pause, back up the database, `pip install` the tag archive (a zip from GitHub, so the machine needs no git), let the new code migrate the schema, resume, and if the new version fails to start restore the database and reinstall the previous tag. Afterwards `update._restart` starts the agent again, except under a Start at login unit, which restarts it itself (a second copy would run every step twice).

**Stopping the old agent.** `update._stop` takes the pid from `agent.pid` only when that process is alive; otherwise it asks `lsof` who holds `agent.lock`. After SIGTERM it waits up to 20 seconds for the process to exit and raises if it does not, and `_apply` then returns a failure ("the old agent (process N) did not exit") instead of reporting a restart. Why: on 2026-11-07 Prod `agent.pid` named a dead process, so the update signalled nothing, the old agent kept its port and the Updating page waited for a restart that never came.

**The update button waits for the restart.** The banner's Update now button (source installs) posts `/update`, which starts one `agent update --yes` process and goes to `/updating`. Progress lives in store key `update_status` (`installing`, `restarting`, `failed`, with the version it started from). `update.in_progress` makes repeat clicks a no-op while a run on the same version is under 15 minutes old; before this, each click started another installer, and the dashboard showed the same banner until the agent went down mid-restart. `/updating` polls `/api/update-status` every two seconds, treats a failed fetch as the restart in progress, and opens the dashboard when the version changes, so no one has to refresh a tab.

**Dashboard week choice.** The week table shows this week or next (`status.week(weeks_ahead=...)`). The choice is stored as `dashboard_week` with the Monday of the week it was made in, and `/dashboard` ignores it once that Monday is past. We keyed it to the week instead of running a timer, so the reset needs no background job and survives the agent being asleep over the weekend. The Hide done and Hide skipped filters are not remembered. Hide done and Hide skipped are remembered the same way in `dashboard_hide`; they are saved only when the filter form is submitted (`f=1`) and both start hidden. A plain visit never changes them.

**Python install path.** `install.sh` and `install.ps1` are the supported install (the desktop app was retired after 0.11.3: macOS kills the ad-hoc signed bundle, and nobody ran it). They check `requires-python`, print install steps when Python is missing, build a private venv under `~/.sc-activity-agent-app` (the data folder stays separate and is never touched by an update) and run `agent install-app`. `awake.py` runs `caffeinate -i -s -w <agent pid>` from the run loop while the Keep awake setting (default on, macOS only) is on: plans only run while the machine is awake. `-w` ends it with the agent, and the loop stops or starts it when the setting changes. `agent run` takes a lock on `<data folder>/agent.lock` (`launcher.lock_data_dir`: flock, msvcrt on Windows) and exits if another agent holds it, because the launcher and the Start at login job can both start an agent within seconds of each other and two agents on one database would run every step twice; the OS drops the lock when the process dies, so a crash never leaves a stale lock. The launcher (`launcher.py`) runs `agent open`, which starts `agent run` when the port is closed and shows an alert naming agent.log when it cannot. `pyproject.toml` lists the web templates and styles as package data: without it a pip install had no console pages.

**Localhost only, secrets encrypted.** The console binds to 127.0.0.1 with no login. Secrets are Fernet-encrypted in SQLite with a key file in the data folder.

### Telegram alerts
Why outbound only: the agent runs on a user's laptop with no public address, so alerts are `sendMessage` calls and button taps are read with `getUpdates` long polling in a daemon thread. Why one bot per instance: Telegram lets one program read a bot's updates, so Prod and SB2 each have their own token (`alerts_token`, encrypted) and settings (`alerts`), and messages carry a [PROD]/[SB2] tag. Why limits: 6 h cooldown per alert key and 10 messages an hour with one summary, so a bad night cannot flood a phone. Why a chat check: only the saved `chat_id` may tap; Cancel WO needs a yes; a stale button re-reads the live step state. A failed send is stored in `alert_error` and never stops the engine. Taps are logged in `changes`.

## Data model
`connections` and `users` hold integration apps and their users. `users.can_do` is a JSON list of actions the user may do (set with the Can do checkboxes on Connections). The old `roles` table is gone (migration 4, B-76); migration 1 creates it only to convert old rows. `locations` describes where the agent works. `work_orders` and `steps` hold each WO and its plan. `api_log` is the audit trail. `settings` holds everything else as JSON.

**Setup guidance.** `setup_checks()` returns `(label, done, link, help, required)`. Setup lists the help text for every open step. The Rank 1 step is not required because the `rank1` cache is only filled by the first creation pass. `ERROR_HINTS` + `hint()` map known error text to the fix and are used on the Errors page (failed steps and creation errors) and in connection-flow messages.

**Creation failure alert (B-86).** `Creator.tick` counts failed creates in store key `create_streak` (reset by any success) and at 3 calls `Alerts.create_failed`. Why: a failed create is skipped and touches no step, so `step_failed` never fires and Prod could make nothing for days unnoticed. The 6 hour per-key cooldown keeps it to a few alerts a day; the streak is counted across locations, so one healthy location hides a broken one (a known limit).

## Known limits
- **Refrigerant assets (B-94):** a `universalCheckOut` on a WO with a refrigerant asset (the HVAC RTU, the only HVAC type seeded) leaves it in COMPLETED / PENDING REFRIGERANT USE. The subscriber review then gets 940 ("RefrigerantWasUsed should be Yes or No") and the invoice gets 904. No API call that answers it is known: the field is refused on the review status call in every shape tried. So `assets.pick` skips refrigerant types (`_refrigerant_types`, from the catalog), and a step refused with that text fails at once (`engine.refrigerant_hold`, hint in `hints.py`) because a retry cannot clear it. `preflight` also parks a WO whose live Extended status holds REFRIGERANT (B-102): the step fails at once with one message, so no later step runs into 921 or 904. Remove all three when B-94 finds the call.
- **Checklists:** the agent cannot create a checklist (no endpoint); a person sets one up in ServiceChannel, and with none for the trade and location the agent does nothing. `TechnicianID` is a fixed 1 because our users store no ServiceChannel user id. Whether a check-out is blocked by unanswered required questions is unknown, because the agent answers all of them. Not run on Production.
- **Photo library:** 75 sets (0.20.9 added eleven for Kitchen Equipment and Freight Equipment, so every RequireAttachment issue has a set), about 23 MB, AI-generated. The 40 older sets mostly show a bundle of colored cables beside the subject, which repeats across scenes; the 12 added in v0.14.3 have none. Replace a set by overwriting its three files and keeping its manifest id. `photos.BY_ISSUE` maps the lower-cased "equipment problem" text of the WO to sets by regex; the first matching rule wins and only its sets tagged with the WO's trade count, so a rule never sends a plumbing photo to an electrical WO. Rules go from specific to general because words overlap ("ice" in "service", "power" in generator outages); use word boundaries. Generated images carry a burned-in BEFORE/AFTER label in varying places, so crop it out per image when splitting, or ask for none.
- The invoice reject-then-resubmit path ran live on SB2 in B-12 (rate flaw, reject, clean resubmission, approve). The hours-flaw path also ran live. Negative lines (credit memo) have not. The invoice number includes a per-WO counter so a resubmission is not a duplicate.
- `docs/api-notes.md` lists what is verified on SB2 and in Production.
- Locations come from a list the app loads from the Subscriber (`GET /odata/locations`, paged 50 at a time, cached in the `locations_cache` setting). The user adds or removes from it, so nobody types ids; a typed Prod id that differs from SB2 would break the contract check and every create. Verified on SB2: 50 locations, response wrapped in `value`, paging stops on an empty page.
- **SB2 copy only from Production.** An SB2-first install cannot add Production, because the SB2 copy hangs off the Production instance. Two programs run while SB2 is on, each with its own rate limit.
- **No import tool; moving an instance is a folder copy.** Stop it, copy its data folder (`agent.db`, `secret.key`) to the new machine and start the agent there. The environment and port live in the DB. Remove the old login item so two agents never act on the same plans.
- **Step failures:** the engine fails any step whose handler raises, not only API errors, so a handler bug cannot loop on one step forever. Each loop in `agent run` (steps, update check, creator) also catches its own errors so one failure never stops the others.
- **Proposals:** the Provider creates the proposal (it has no WO field), and the Subscriber links it with assignWO before approving, because assignWO is Subscriber-only.
- **Invoices are line items, and the Subscriber checks them (B-12).** `invoice_submit` bills Labors (hours = time on site rounded to 0.5, minimum 0.5, at the agreed rate) plus 0 to 2 Materials lines, kept under the NTE. The API refuses a total above the NTE (error 1104) and a second invoice while one is OPEN or APPROVED (error 1105), so over-NTE, partial and credit-memo invoices cannot be made on one WO; they are out of scope. The agreed rate comes from the WO context, then the `agreed_rates` store cache (`<provider>:2`), then a random pick from 65/75/85/95. After each POST the agent reads the invoice back and learns `Labors[].AgreedRate` into that cache, so later invoices bill the contract rate. Two settings, `invoice_rate_flaw` and `invoice_hours_flaw` (default 0, Behavior sliders), make the first invoice bill a wrong rate or extra hours; the plan then always rejects it and resubmits a clean one. `invoice_decide` also rejects on what it sees, even when the plan said approve: the live invoice has `WithMismatchedRates`, or billed hours exceed time on site x 1.25 + 0.5 (the API has no hours check, so that rule is the agent's own). It inserts a resubmission and a decision after 1 to 2 days, at most 3 invoices per WO. When the live invoice is already APPROVED or PAID (a person decided first), the planned resubmit and its decision are skipped, because a second invoice while one is APPROVED returns 1105; a resubmit that still gets 1105 (approved between the two steps) ends as done, not failed. A REJECTED invoice keeps its resubmit. Why read the flags instead of trusting the plan: it makes the reject path follow real data, the way a Subscriber would. **No NTE, no invoice:** `invoice_submit` reads the live WO first. An NTE of 0 means the API refuses any invoice (error 1104), so the Subscriber sets COMPLETED/NO CHARGE (verified on SB2, WO 359213720; the API also reports `CanCreateInvoice: false`), the WO state becomes `closed` and the remaining steps are skipped. Before this, such a WO failed with a misleading 917, because the fallback user's error hid the real 1104.
- **The user may act first:** `proposal_decide` and `invoice_decide` read the live status before acting. If the user already did what the plan wanted, the step is done and the plan continues. If the user rejected a proposal the plan meant to approve, the plan adds a revised proposal and decision (at most 3 times, then the step fails for the Errors page). A decision the user already made is never overturned, because the API allows an approve after a reject. `invoice_pay` runs as the same Subscriber user as `invoice_decide` (so existing instances need no new role row), pays only an invoice that is still APPROVED, and waits `pay_days` (default 30, spread about 25%) after the approval, because Net 30 is the common term. A WO therefore stays active for a month after its decision and shows as Payment due until then. It quietly skips a Subscriber the API says cannot record payments (error 1178 "Pay not allowed"). Every write step first runs `preflight` (one GET of the live WO): a cancelled WO ends the plan before any write, and a WO a user already completed skips accept, check-in, check-out and proposal steps (review and invoice still run). The same read follows user edits (`follow` in `handlers/guard.py`): a new NTE or priority goes into the saved context, which the invoice and proposal amounts and the notes read; a later scheduled date moves the first pending check-in and every step after it by the same amount (the visit snapped into activity hours on a weekday, so spacing and the check-out day hold), and a check-in that is itself due waits for its new time without counting an attempt (`Later`); a status outside OPEN, IN PROGRESS, ON HOLD and COMPLETED, or a provider other than the one the plan was built for, parks the plan (`Park`): the step fails at once with no retries, so it shows on the Errors page, and Skip carries on or the WO can be cancelled. The baseline date (`sched` in the context) is the live date at the first preflight, because a created WO's date passes through time-zone conversion and would not compare equal to the plan; the agent's own reschedule clears it so the next read re-seeds it. A failed preflight read is ignored and the step runs; a refused write re-reads the WO in `guarded` as before. Why read first instead of reacting to a failure: some writes on a changed WO succeed or leave odd audit entries, and one GET per step (about 12 per WO) is far cheaper than polling every WO. A `watch` pass (setting `status_check`, a Settings toggle, default on; every 3600 s, 1 WO per pass, least recently watched first) ends the plan of a WO a user cancelled in ServiceChannel without waiting for the next step to come due. It only reads. It is a toggle, not a Behavior slider, because it has no rate to tune.

**Declines and reschedules (B-11):** `decline` and `reschedule` use the Provider's `accept` capability (no new checkbox). A decline plan is only `decline` then a Subscriber `cancel` 1 to 3 days later (reason 1, 2, 3 or 6; reason 5 needs custom text; the decline has no `Note` because that returns 501). A reschedule plan puts the original date in the WO at creation (`reschedule.from_ts`, read by `Creator.create`), then moves it later with `PUT /workorders/{id}/scheduledate`; the visits are planned on the new date, and a provider note explains the change. Reschedules are skipped for emergency, proposal and late plans. Whether a decline shows OPEN / DECLINED depends on the trade's auto-reassign setting (api-notes). B-20 builds on this. **Reassign (B-20):** with the Behavior setting "Reassign after a decline %" (default 0), a declined plan is `decline` then `reassign` instead of `decline` then `cancel`. The target cannot be known at plan time, because it depends on which other provider connections hold a contract for the trade at the location, so the `reassign` step decides when it runs: it looks up `GET /contracts` for each other provider connection that has a user who can accept, and `PUT /workorders/{id}/reassign` (Subscriber; body `ProviderId`, `ReasonId`) moves the WO to one of them. The API refuses the move without a contract for that trade, so the lookup comes first. After a move the step saves the new `provider_id` in the WO context (so later steps use that provider's users only) and inserts a fresh normal plan after itself. It first marks the old plan's remaining pending steps skipped, because they belong to the old provider (a check-out for a visit that never happened would fail). The same step serves the no-show outcome: with "Provider no-shows %" the plan is accept, the usual ETA note, a Subscriber note a few hours after the visit time, then `reassign` carrying `cancel=noshow_cancel`, so a failed move cancels with a no-show note instead of the decline note. The new plan runs with decline, reschedule, reassign and no-show all at 0 so a WO cannot chain moves. A reassign works from any status (SB2 accepted it while the WO was on site and put it back to OPEN), so the step does not check the plan's position. The Rank 1 cache stores `owners` (trade to provider id) so every WO gets its provider recorded; an older entry without it is re-read, and adding or removing a connection clears the cache. When no provider qualifies, or the API still refuses, it inserts the `cancel` step a decline would have had. Spike results are in api-notes.

**Emergency plans (B-08):** `planner.build_plan(..., eta=...)` treats an ETA at most `emergency_hours` after the call date (default 8, 0 = off) as an emergency; the priority label never decides. `Creator.create` picks a same-day ETA for EMERGENCY issues (we choose the ETA of the WOs we create, so the label is only the trigger for that choice), and `cleanup.finish_plan` reads the WO's real `CallDate` (or `CreatedDate`) and `ScheduledDate`, and only counts a visit still ahead. The accept moves to 2 to 15 minutes, a subscriber follow-up and a provider ETA note form the confirm-availability exchange, the first check-in lands under about 8 hours out (fitted to activity hours), and proposals and late arrivals are switched off, since an urgent visit that waits days for a proposal looks fake.
- **One command surface for changes:** settings and plan edits (`get`, `set`, `plan`, `step`) go through the CLI and the same SQLite store the console uses, and each change is logged in the `changes` setting. A person, the console or an assistant acting for the user all use it, so nobody edits the database by hand. The handlers also stop at a WO the user cancelled or completed (`guarded` in `handlers/guard.py`).
- **Every planned step is fitted to the activity window.** The planner draws times by adding random offsets to the creation time, so notes, review and invoices used to land at night and on weekends. `planner._fit` moves any step outside the window to the start of the next business day and keeps the order, spreading consecutive moved steps a few minutes apart. Moving by time-of-day was tried first and failed: evening steps landed late in the afternoon and pushed the next morning's check-in past closing. A step moved to a window start gets 0 to 90 minutes of jitter (capped at half the window), because without it every WO's overnight steps landed on exactly the opening minute (Prod, 2026-11-07: 10 to 14 steps due at 08:00:00 on each coming day); `Engine.snap` (sleep gaps, rework return) still snaps to the exact start, a known limit. Plans already saved keep their old times; re-time them by hand (`agent step <id> due ...`) if it matters.

**Scripts.** `scripts/bump_version.py X.Y.Z` sets the version in every file that carries it and fails if a pattern matches the wrong number of times; the version-sync test checks the result. `scripts/live_sb2.py` creates one work order on an SB2 instance and runs its whole plan with every step due now (refuses Production); run it before a release to catch API drift that unit tests cannot. `--photos`, `--checklists` and `--rework` switch on the matching write paths for the run; `--rework` rates every review and makes the first one unsatisfactory.
